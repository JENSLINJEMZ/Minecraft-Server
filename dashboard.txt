# Build MinePulse — Premium Minecraft Server Monitoring Platform

Act as a senior full-stack engineer, Java Paper plugin developer, UI/UX designer, and application security engineer.

Build a complete, production-minded Minecraft server monitoring platform called **MinePulse**. This is a private monitoring dashboard for my own Minecraft Paper server, with a custom Java plugin that sends detailed telemetry to the web application.

Do not build a static mockup. Implement the frontend, backend, database, Java plugin, authentication, real-time data flow, historical analytics, alerts, logs, and plugin inventory. Every interactive control must perform a real action or clearly indicate when a feature is not configured.

## 1. Product goals

The application must allow an authenticated administrator to:

- Monitor whether the Minecraft server is online and connected.
- View live TPS, MSPT, memory usage, player count, and uptime.
- Inspect historical performance charts and player activity.
- Detect performance degradation and server disconnects.
- Configure alerts and receive Discord notifications.
- Browse server events and monitoring logs.
- Inspect installed plugins and their reported versions.
- Track join and leave events and player session history.
- View data freshness and plugin-to-backend connectivity.
- Export selected historical monitoring data.
- Manage monitoring settings and API credentials securely.

The first release targets a single Minecraft Paper server. Structure the code so multiple servers can be supported later without rebuilding the application.

## 6. Performance monitoring

Create a dedicated performance page.

Track:
- TPS, including the available 1-minute, 5-minute, and 15-minute values when supported by the selected Paper API.
- Current and rolling MSPT.
- JVM heap usage, maximum heap, and committed heap.
- Garbage collection activity if it can be measured reliably.
- CPU usage when a reliable source exists.
- Process uptime and server uptime.
- Player count and maximum capacity.
- Optional disk and network metrics supplied by a separate trusted host agent.

Show:
- Historical time-series charts.
- Current readings and trends.
- Configurable time windows.
- Performance warning annotations.
- A timeline of restarts and incidents.
- Clear explanations of missing metrics.

For tick performance, a 20 TPS server targets 50 milliseconds per tick. Treat sustained high MSPT and reduced TPS as performance warnings rather than assuming one measurement proves a problem.

Do not claim the Paper plugin can measure host-wide CPU, disk I/O, or network traffic accurately without a suitable source.

Use bounded data collection and aggregation. Do not retain a full high-frequency metric sample forever.

## 10. Alerts and Discord notifications

Build a functional alert management page.

Support configurable rules such as:
- Server heartbeat missing.
- TPS below a configurable threshold.
- MSPT above a configurable threshold.
- Heap memory utilization above a configured percentage.
- Player count reaches a threshold.
- Server agent disconnected.
- Repeated performance incidents.

Each rule must support:
- Enable or disable.
- Threshold.
- Evaluation duration.
- Severity.
- Cooldown.
- Recovery notification.
- Last triggered timestamp.
- Last delivery status.

Use a backend alert evaluation service with hysteresis or consecutive-sample evaluation to prevent alert flapping.

Detect server offline state using a configurable heartbeat timeout. Distinguish an offline server from a telemetry agent that has stopped communicating.

Implement Discord webhook notifications using a backend-only secret. Never send webhook URLs to the frontend or log them.

Add a test notification action, with rate limiting and safe failure handling.

If notification delivery fails, record the failure and retry only within a bounded retry policy.

## 11. Custom Paper plugin: MinePulseAgent

Build the complete Java plugin.

Responsibilities:
- Read configuration.
- Register player join and quit listeners.
- Collect supported server metrics.
- Report server identity, version, and plugin inventory.
- Send an initial registration or heartbeat.
- Send periodic telemetry at a configurable interval.
- Retry transient HTTP failures with exponential backoff and jitter.
- Maintain a local connection state.
- Shut down scheduled tasks cleanly.
- Never block the main server thread on HTTP requests.
- Avoid logging secrets.
- Avoid unbounded queues and uncontrolled telemetry generation.

Suggested configuration:

backend-url: "https://YOUR-DASHBOARD-HOST"
server-id: "YOUR-SERVER-ID"
agent-token: "SET-THIS-SECRET"
heartbeat-interval-seconds: 15
metrics-interval-seconds: 10
plugin-inventory-interval-seconds: 300
connect-timeout-ms: 3000
request-timeout-ms: 5000
debug: false

Use placeholder values and document how to provision the real token securely.

The agent should send:
- Server ID.
- Timestamp.
- Agent/plugin version.
- Minecraft and Paper versions.
- Online player count and maximum capacity.
- Online player UUIDs and usernames when needed for session tracking.
- Supported TPS readings.
- MSPT measurements.
- JVM memory statistics.
- Server uptime.
- Plugin inventory when requested or on a scheduled refresh.
- Structured player and server events.

Use bounded rolling calculations for MSPT when the Paper API does not expose the desired measurement directly. Document how the measurement is calculated.

Do not send a complete plugin inventory with every heartbeat. Cache the inventory and refresh it on a separate interval.

All telemetry requests must have:
- Server ID.
- Timestamp.
- Request ID or sequence identifier.
- Schema version.
- Authentication.
- Payload validation.

Use an authenticated TLS connection. Support credential rotation and server-side revocation.

Never allow the monitoring plugin to execute arbitrary commands received from the website. The initial product is read-only monitoring.

Requirements:

The UI must remain usable if WebSockets are temporarily unavailable. Implement an HTTP fallback for current status and historical queries.

## 15. Data retention and performance

Implement a configurable retention policy.

Suggested initial defaults:
- Raw metrics: retain for 7 days.
- Aggregated 1-minute metrics: retain for 30 days.
- Aggregated 1-hour metrics: retain for 180 days.
- Events: retain for 30 days, with configurable exceptions for alert incidents and audit records.
- Player sessions: retain according to a configurable privacy policy.

These are defaults, not hardcoded guarantees.

Implement scheduled cleanup and aggregation jobs. Make them idempotent and safe to retry.

Use parameterized database operations. Avoid querying every raw sample when a chart requests a long historical range.

Expose data freshness in the UI and reject or flag invalid, future-dated, duplicate, or excessively delayed telemetry.

## 16. Security requirements

This dashboard is private and must not be publicly writable.

Implement:
- Secure password hashing using Argon2id or an equivalent established password-hashing algorithm.
- Secure, HTTP-only, SameSite cookies.
- HTTPS in deployment.
- CSRF protection when required by the cookie-based authentication design.
- Strict CORS allowlists.
- Rate limiting on login and ingestion routes.
- Input validation and output encoding.
- Authorization checks on every protected resource.
- Environment variables for secrets.
- A .env.example containing placeholders only.
- Redaction of passwords, tokens, webhook URLs, and sensitive headers.
- Audit logging for administrative changes.
- Dependency and configuration checks.
- Secure WebSocket authentication.
- Token rotation and revocation.
- Safe error messages without stack traces in production.

Do not store plaintext agent tokens in the database. Do not hardcode credentials in the frontend or plugin source. Do not commit .env files.

For local development, provide a safe bootstrap procedure to create the first administrator. Do not expose a public registration endpoint by default.

The dashboard should bind to localhost by default for local development and require an explicit secure deployment configuration for remote access.

## 19. Acceptance criteria

The project is complete only when:

1. The dashboard builds and starts using documented commands.
2. The API and database initialize successfully.
3. An administrator can log in and log out securely.
4. The Paper plugin compiles into a distributable JAR.
5. The plugin can authenticate and send telemetry to the API.
6. Actual server metrics appear in the dashboard.
7. Disconnecting the agent changes the connection status after the configured timeout.
8. Historical charts query persisted data.
9. Player sessions and plugin snapshots are stored correctly.
10. An alert can trigger and resolve based on actual collected metrics.
11. Discord delivery can be tested when configured.
12. Unauthorized API and WebSocket access is rejected.
13. The application distinguishes unavailable data from healthy measurements.
14. The retention process removes eligible data without corrupting aggregates.
15. Tests cover authentication, ingestion, metric persistence, alert evaluation, and critical UI states.
16. No production dashboard feature depends on hardcoded demo data.
17. Documentation explains how to configure, install, secure, test, and troubleshoot the system.
